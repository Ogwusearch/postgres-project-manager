## 1. Objective

Improve the admin web application's tenant-specific workspace data handling so that switching between tenants does not expose stale project or database-instance data.

The work focused on:

1. Hiding workspace data when it does not belong to the currently selected tenant.
2. Preventing obsolete asynchronous requests from overwriting data for a newer tenant selection.
3. Separating workspace-loading logic from the React component.
4. Adding regression tests.
5. Verifying the changes and committing them.

## 2. What We Completed

### 2.1 Tenant-specific workspace visibility

Created:

### 2.2 Asynchronous workspace loading

Created:

`apps/admin-web/src/workspace-data-loader.ts`

Extracted the asynchronous loading process into a separate, testable function.

The loader:

- Requests projects from `/api/projects?limit=100&offset=0`.
- Requests database instances from `/api/database-instances`.
- Sends the selected tenant through the `X-Tenant-Id` header.
- Uses included credentials for the requests.
- Handles unsuccessful responses and errors.
- Checks cancellation before publishing results or updating completion state.

Updated:

`apps/admin-web/src/App.tsx`

The React component now uses the extracted loader and supplies callbacks to update the workspace state.

### 2.3 Tenant-switching regression test

Created:

`tests/workspace-data-loader.test.ts`

Added a regression test that simulates this sequence:

1. Start loading Tenant A.
2. Switch to Tenant B before the first requests finish.
3. Switch back to Tenant A before the second requests finish.
4. Resolve the obsolete requests after the newest request has started.
5. Verify that only the latest, active Tenant A request publishes results.

**Result:** The test passed. The cancelled requests did not publish stale results or trigger their completion callbacks.
